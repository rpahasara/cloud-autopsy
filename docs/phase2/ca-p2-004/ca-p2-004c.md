# CA-P2-004c — recorded Kubernetes evidence adapter (implementation record)

**Scope:** the third slice of CA-P2-004 (see the [Phase 2 backlog](../../reviews/phase1d/phase2-backlog.md#status)), stacked on [004b](ca-p2-004b.md). It adds a strictly offline adapter. The adapter converts **recorded** Kubernetes API list responses into the existing contracts, written as an evidence bundle ([004a](ca-p2-004a.md#bundle)) that the existing loader, creation path, API and dashboard accept unchanged. It is synthetic-only, under the product owner's [pre-gate development authorization](../ca-p2-003/ca-p2-003b-1.md).

The product owner chose **existing contracts only** for this slice:
- observation kinds stay at `ca-observation-kinds/0.1-provisional`;
- there is no migration `0006`;
- every contract version, frozen fixture and pinned result digest is unchanged.

Kubernetes Events and ConfigMap metadata are therefore parsed, validated and counted, but classified `unsupported_conversion`. First-class kinds for them are a separate, versioned follow-up: [ca-p2-004c-kinds-followup.md](ca-p2-004c-kinds-followup.md).

**Not included:**
- live Kubernetes access, a Kubernetes client, cloud credentials or network use;
- API write routes, new dependencies, schema or contract changes;
- a UI redesign;
- customer or real-cluster recordings.

This is not a gate approval, a collector, or a production-readiness claim.

## <a id="format"></a>Recording format `ca-k8s-recording/0.1-provisional`

A recording is a directory with `recording.json` and one `responses/<name>.json` per recorded list response. The bodies stay exactly as recorded (for example `kubectl get -o json` output): they are parsed strictly, but need not be canonical.

| Manifest field | Meaning |
|---|---|
| `recording_id`, `source_id`, `cluster_id`, `namespace` | Identity and the single registry binding. Every recorded object must be in this namespace |
| `data_classification` | Must be `synthetic` |
| `window` | The plan window (at most 1 hour) |
| `clock` | The recording's declared API-server clock (`declared` with a fixture-declared offset and uncertainty, or `unknown`) |
| `responses[]` | One per resource: `pods`, `replicasets`, `deployments`, `events`, `configmaps`. Each has `http_status`, `error` (`timeout`, `rate_limited`, `unavailable` or null), and, for HTTP 200 only, `file`, `sha256` and the recorder-declared `coverage` (inside the window) |

## <a id="conversion"></a>What is converted (observation kinds 0.1, unchanged)

| Planned acquisition | Recorded resources | Observation kinds |
|---|---|---|
| `k8s.pods` | `pods` | `pod`: owner ReplicaSet, node, summed restart count, ConfigMap volume mounts (names and paths only) |
| `k8s.deployments` | `deployments` + `replicasets` | `replicaset` (owner Deployment, revision, image), and `deployment_rollout` from the Deployment's current revision and the newest older ReplicaSet revision owned by the same Deployment UID |

How each value is derived:
- **Rollout fields.**
  - The images, ConfigMap references and changed template fields come from the two recorded ReplicaSet templates. Only field paths are reported, never values.
  - The rollout's event time is the new ReplicaSet's `creationTimestamp`.
  - Its completion time is the Deployment's `Progressing/NewReplicaSetAvailable` condition, when recorded.
  - A Deployment with no older revision has no rollout to describe (`notes.no_previous_revision`).
- **Timestamps** stay as recorded raw text in the recording's clock domain, with their declared precision: one second, or the precision of the recorded fraction. An unparseable timestamp is kept as raw text and left unplaced. Nothing is reordered or inferred.
- **Out of scope:** items whose controller owner is outside the query's scope, such as a Pod with no ReplicaSet owner, are counted `out_of_scope` in the report and never dropped silently.
- **Identity:** evidence IDs come from the single registry source, which fixes the cluster and namespace. The same object recorded through a different binding is a different identity, as before.

## <a id="unsupported"></a>Events and ConfigMaps: `unsupported_conversion`

- **Validated, then counted:**
  - Events: shape, involved object, namespace, type and reason. They are counted by involved kind and type (for example `Pod/Warning: 1`).
  - ConfigMaps: their metadata. They are counted, along with the number of data keys.
- **Not planned:** no acquisition is planned for them, the registry lists no query for them, and no batch is written for them. So **no coverage is claimed** and **nothing from them can be cited or used for a conclusion**. The report marks each with `coverage_claimed: false` and `used_as_evidence: false`.
- **Values are never read.** The Secret scan skips `data`, `binaryData` and `stringData`. ConfigMap values, annotations and event messages are never copied into a bundle, a report or a result. Tests check for placeholder values, `last-applied-configuration` content and event text.

## <a id="honesty"></a>Responses, failures and refusals

| Recorded response | Acquisition outcome | Coverage |
|---|---|---|
| HTTP 200 with a valid list and no continuation token | `complete` (observations) or `empty` (none) | The recorder-declared coverage. For `k8s.deployments`, the intersection of both resources' coverage, and `failed`/`invalid_response` if they do not overlap |
| HTTP 200 with a continuation token | `partial`, `page_limit`, truncated (`omitted_count` from `remainingItemCount`) | Not verified |
| 401 or 403 | `denied`, `authorization_denied` | None |
| 429 | `failed`, `rate_limited` | None |
| 504 or `timeout` | `failed`, `timeout` | None |
| Any other failure, or a resource that was not recorded | `failed`, `source_unavailable` (`not_recorded` in the report) | None |
| A body that is not strict JSON, has the wrong list kind or duplicate items, or contains any item that cannot be converted | `failed`, `invalid_response`, with the item error code in the report | None |

**Refused outright** (`RecordingError` with a stable code; nothing is written):
- a non-synthetic classification;
- unknown, duplicate or missing manifest fields or resources;
- any Secret resource or Secret object;
- an object or event in another namespace;
- unsafe paths, links, junctions or unlisted files (the bundle loader's checks are reused);
- digest mismatches and oversize files.

## <a id="report"></a>Conversion report `ca-k8s-conversion-report/0.1-provisional`

The report is canonical JSON, written outside the bundle (the bundle holds only its listed files). It records the recording's SHA-256 and the plan digest, plus:
- **for each converted acquisition:** its resources, the response per resource, the outcome and reason, the observation count, `coverage_claimed`, the `out_of_scope` counts, item error codes and notes;
- **for each unsupported resource:** its classification, response, item count and counts.

It never carries recorded values.

## <a id="cli"></a>Command line

```bash
python -I tools/convert_k8s_recording.py examples/k8s-recordings/rollout-complete --out OUT_DIR --report OUT.json
```

```bash
python -I tools/create_investigation.py --offline OUT_DIR
```

Database-verified creation and the dashboard work as for any bundle (`--serve`). Exit status: 0 converted; 1 refused, with nothing written; 2 usage. `tools/export_k8s_recordings.py` regenerates the examples.

## <a id="examples"></a>Synthetic examples (`examples/k8s-recordings/`)

| Recording | Responses | Result |
|---|---|---|
| `rollout-complete` | All five lists, HTTP 200 | `k8s.pods` complete (2 pods; 1 out of scope); `k8s.deployments` complete (2 ReplicaSets, 1 rollout); Events and ConfigMaps counted, unsupported |
| `degraded` | Pods truncated; ReplicaSets 503; Events 504; ConfigMaps 403 | `k8s.pods` partial; `k8s.deployments` failed (`source_unavailable`); no coverage claimed for either |
| `events-only` | Pods 403; Events and ConfigMaps 200; nothing else recorded | Both acquisitions denied or failed with no evidence; 3 events and 1 ConfigMap counted, unused |

All three investigate offline and in the database with outcome `abstained`. Only Kubernetes state was converted, so no symptom was observed.

## <a id="tests"></a>Tests

- **`tests/app/test_k8s_recording.py`** (offline CI job):
  - **Examples:** they equal a fresh export. Conversion is deterministic and pinned (bundle manifest, report and offline result digests).
  - **Contracts:** observation kinds and their set are unchanged.
  - **Conversion:** Pods, ReplicaSets and rollouts become existing kinds with the correct fields and a single registry binding. Raw timestamps and their precision are kept, including an unparseable one.
  - **Unsupported records cannot create coverage or evidence:**
    - they are never planned, in the registry, in a batch or in the frozen acquisitions;
    - adding 20 more Warning events that "name" a cause, or removing all events and ConfigMaps, gives a **byte-identical bundle and result**;
    - an events-only recording has no timeline entries and no cited evidence;
    - every cited evidence ID comes from a converted kind.
  - **No leaks:** ConfigMap values, annotations and event text never appear in bundles, reports or results.
  - **Honest failures:** 401, 403, 429, 504 and 500 responses; missing resources; truncation; malformed bodies and items (`invalid_response`, never partial); rollouts without their ReplicaSet; non-overlapping coverage.
  - **Refusals:** classification, version, unknown fields, the window limit, Secrets (as a resource or an object), namespace isolation (objects and events), digests, unlisted files, traversal, duplicates, junctions (Windows) and symlinks (Linux).
  - **CLI:** the report is written, and a refusal writes nothing.
- **`tests/integration/test_k8s_recordings.py`** (real-PostgreSQL CI job):
  - all three converted bundles are created as database-verified runs, with bytes equal to offline;
  - the API timeline shows the rollout and pods and not the out-of-scope pod;
  - in a real browser, the runs open in the existing Home (3 granted, 0 resolved, "Verified on read") and Investigation workspace ("Byte-identical replay").
- **CI:** the offline job converts every example and investigates the results.

## <a id="limitations"></a>Limitations

- **Synthetic recordings only.** Real recordings need the privacy and retention decision (CA-DEC-005) and a security review.
- **No first-class Event or ConfigMap-metadata evidence** until the [kinds follow-up](ca-p2-004c-kinds-followup.md). Investigations from recordings alone therefore cannot see configuration changes or event-reported failures, and will usually abstain.
- **Coverage is declared, not verified.** It is what the recorder declared for each list response. A list is a point-in-time snapshot, and the adapter cannot verify that the recorder's coverage claim is accurate.
- **Strict item handling.** Single-container ReplicaSets only for rollouts and images (others make the acquisition `invalid_response`). Unscheduled Pods (no node) make the Pods acquisition `invalid_response` rather than partial. Both rules are deliberately strict, not complete.
- **Single source.** One cluster, one namespace and one API-server clock per recording.
- **No independent review.** These are AI-assisted changes with no independent contract or security review.
