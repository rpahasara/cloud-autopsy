# CA-P2-004d — versioned Kubernetes observation kinds 0.2 and snapshot coverage (implementation record)

**Scope:** the follow-up planned in [ca-p2-004c-kinds-followup.md](ca-p2-004c-kinds-followup.md), stacked on [004c](ca-p2-004c.md). It adds `k8s_event` and `configmap_metadata` as first-class observation kinds in a separate, explicitly versioned kind registry, `ca-observation-kinds/0.2-provisional`, keeping full support for 0.1 investigations. It also audits and corrects the coverage semantics of recorded Kubernetes snapshots. Synthetic-only, under the product owner's [pre-gate development authorization](../ca-p2-003/ca-p2-003b-1.md).

**Not included:** live Kubernetes access, cloud credentials, customer evidence, API write routes, a UI redesign, new dependencies, or deployment. This is not a gate approval, an independent contract review, or a production-readiness claim.

## <a id="preflight"></a>Preflight findings

| # | Finding | Consequence | Resolution |
|---|---|---|---|
| P1 | Every run plan pins `contract_versions` and was required to equal the package's set **exactly** | A new kind-registry version would change every plan, and with it all six result digests | Two explicit **contract profiles**. The baseline (kinds 0.1) stays the default and is byte-identical; the only other profile differs in `observation-kinds` alone. A plan pins one whole profile; anything else is refused |
| P2 | Stored evidence is deduplicated by `(evidence_id, content_digest)`, and the first stored bytes win (`ca.evidence_version`). The record carries `kind_registry_version` | If a 0.2 plan stamped "0.2" on a Pod record, the database would serve the 0.1 bytes to the 0.2 run, or the reverse: re-labelling | A record's `kind_registry_version` is the version that **introduced its kind** (`KindSpec.since`), not the plan's. 0.1 kinds are byte-identical under either plan, and 0.2 kinds are refused under 0.1 plans |
| P3 | The record also carries the source's **binding digest**, which covers the registry's query list and clock domains. Two runs observing the same object through registries that differ only in their query list share one stored row with the first binding. **Pre-existing and latent**; no current fixture overlaps | The second run would seal, then fail verification on read (fail-safe, but late) | **(a)** The adapter uses one registry binding for every kinds version. **(b)** The sealer checks every member's *stored* record against the run's registry before sealing. A mismatch is deterministic, so the run fails as `seal:record_inconsistent` (R4 path from [004b](ca-p2-004b.md)) |
| P4 | `ca.contract_pin` holds one version per contract (primary key) and is append-only | The pin cannot simply be changed or extended | Migration `0006` adds `ca.contract_version_supported` (append-only), plus a trigger refusing a plan row that pins an unsupported version. `check_environment` compares the supported set. `0001`–`0005` are unchanged |
| P5 | Mechanisms dispatch only on `configmap_change` and `deployment_rollout` | New kinds cannot create or change a hypothesis. Letting Events *corroborate* would need a new rule version, and rule versions are pinned in every plan, so all six digests would change | Events and ConfigMap metadata are **timeline context only** in this slice. Corroboration is left to a separately versioned rule change |
| P6 | Recorded list responses were converted with the recorder's declared window as verified coverage (004c) | False completeness: a list is a snapshot, not history | See [Coverage semantics](#coverage) |

## <a id="kinds"></a>Observation kinds 0.2

`KIND_REGISTRIES = {0.1: KINDS, 0.2: KINDS + KINDS_ADDED_IN_V2}`. The 0.1 kind objects are the same objects in 0.2. Identity and content rules are unchanged. Evidence IDs and content digests do not include the registry version, so the vectors use the 0.1 ID and content algorithms.

| Kind | Class | Entity | Attributes | Times | Never stored |
|---|---|---|---|---|---|
| `k8s_event` | `K8S-EVENT` | the Event | `involved_kind`, `involved_name`, `type` (`Normal`/`Warning`), `reason`, `count` (≥ 1), `reporting_component` (nullable) | `event` (lastTimestamp, eventTime or series), optional `first_seen` | the message or note text |
| `configmap_metadata` | `K8S-CONFIG-METADATA` | ConfigMap | `data_key_names`, `binary_key_names` (sets of names; credential-like names refused), `withheld_key_count`, `immutable` | `event` (creationTimestamp) | values, value digests, credential-like key names (the adapter withholds and counts them) |

**Test vectors:** [`ca-observation-kinds-0.2-provisional.json`](../../../src/cloud_autopsy/contracts/vectors/ca-observation-kinds-0.2-provisional.json).
- Expected IDs and digests were computed by an **independent Node.js implementation** ([`tests/contracts/independent/kinds_v2_vectors.mjs`](../../../tests/contracts/independent/kinds_v2_vectors.mjs)) from the documented rules, following the 0.1 vectors' precedent.
- The vectors also cover relations (key-name order is not content; a namespace binding changes identity) and refusals (messages, notes, values, value digests, credential-like names, wrong type, count, entity kind, time kind, namespace).
- Independent human review is still pending.

## <a id="guardrails"></a>Causal guardrails

- **No new mechanism.** Events and ConfigMap metadata appear in the timeline. No mechanism evaluates them, so they can never establish a cause.
- **Proven by tests:** under 0.2, the hypotheses (mechanism, status and change evidence) are identical to the 0.1 conversion of the same recording, and adding 20 Warning events "naming" a cause changes no hypothesis or outcome.
- **Never a configuration change:** `configmap_metadata` never becomes a change, which only `configmap_change` with verified values can be. `config_limit_reduction` is never supported by it.

## <a id="database"></a>Database (migration `0006`)

- **New table:** `ca.contract_version_supported(contract_name, contract_version)`, with one row: `observation-kinds` → `ca-observation-kinds/0.2-provisional`. It is append-only (`forbid_mutation`), and SELECT is granted to the runtime roles.
- **New trigger:** `ca.check_plan_contract_versions()` (not `SECURITY DEFINER`, no EXECUTE for PUBLIC) refuses a `ca.run_plan` row whose stored plan pins a version that is neither the baseline pin nor a supported version (`23514`).
- **Environment check:** `ingest.check_environment` now also requires the supported set to equal the package's.
- **Older packages:** a 0.1-only package would still pass its own checks against a `0006` database, but it cannot decode a 0.2 run. Such a run reads as unverifiable, never as reinterpreted.

## <a id="adapter"></a>Recorded Kubernetes adapter

- **Kinds versions:**
  - `convert(recording, kinds)` and `tools/convert_k8s_recording.py --kinds 0.1|0.2`.
  - Under 0.2, `k8s.events` and `k8s.configmaps` are planned as **optional** acquisitions and converted into the new kinds.
  - Under 0.1 (the default), they stay `unsupported_conversion` exactly as in 004c.
- **Snapshot recordings only:** kinds 0.2 needs a snapshot recording (`ca-k8s-recording/0.2-provisional`).
- **One registry binding for every kinds version** (P3a), so evidence shared between 0.1 and 0.2 runs is byte-identical.

## <a id="coverage"></a>Coverage semantics (audit and correction)

| Kind of knowledge | What it proves | How it is represented now |
|---|---|---|
| **Point-in-time snapshot** (a list response) | What existed at one instant | Recording 0.2: `snapshot_at` per response. A complete or empty acquisition covers exactly `[snapshot_at, snapshot_at + 1 ms)`. The rest of the window is a `coverage_gap` |
| **Recorded historical evidence** (timestamps in the objects) | That something happened at a recorded time | Kept as evidence with its raw time and precision. It never implies coverage |
| **Verified continuous acquisition coverage** | That nothing else happened in an interval | Only a source with a continuity guarantee (a watch with an unbroken cursor), which no recording here provides. Nothing claims it |
| **Unknown or unavailable periods** | Nothing | `coverage_gap`, or `failed`, `denied` or `partial`, never `empty` |

**Correction (no contract change):**
- **Recording 0.1:** a recorder-declared window is converted as `partial` with `continuity_lost`, so the window is never counted as covered. This changes the **unmerged** 004c example outputs, which were re-pinned. No stored record or the six scenario digests change.
- **Recording 0.2 (new):** each response records its own `snapshot_at`.
- **Different snapshot instants:** if the resources one acquisition needs (Deployments and ReplicaSets) were listed at different instants, they cannot be joined into one verified view, so the acquisition is `partial` (`continuity_lost`).

**Separate follow-up:** representing *continuous* coverage (for example, a watch-based collector with cursor continuity and declared retention) needs collector semantics and probably a batch-contract change, so it stays separate (CA-P2-004e or later).

## <a id="review"></a>PR #31 review: cross-run rejection (P1), fixed by migration `0007`

**Finding.** The P3 guard above made the latent defect fail early, but it also **rejected legitimate runs**. The cause:
- `ca.evidence_version` is keyed by `(evidence_id, content_digest)` and keeps the first delivery's bytes, which carry that delivery's source-binding digest.
- So any later run that re-observes unchanged objects through an **evolved registry** (one more query, another clock domain) was failed at seal, as `seal:record_inconsistent`.
- A real collector re-observes unchanged objects constantly, and registries evolve. Once objects overlapped, every investigation after a registry change would have been blocked.

**Reproduced first:** commit `75f8c19`, CI run [43197665222](https://github.com/rpahasara/cloud-autopsy/actions/runs/43197665222), failed with `SealFailed: run failed: seal:record_inconsistent`.

**Fix (additive, forward-only):** migration `0007_evidence_binding_records.sql`.
- **New table:** `ca.evidence_binding_record(evidence_id, content_digest, source_binding_digest, record_bytes)`. It is append-only, with INSERT for `ca_ingest` and SELECT for `ca_sealer`. Ingest also stores the record as delivered under its binding.
- **View change:** `ca.sealed_evidence_record` keeps the same columns but returns the record bound to the run's own registry source. It falls back to `ca.evidence_version` only for runs ingested before `0007`, which read exactly as before.
- **Nothing rewritten:** no existing row changes. The first stored bytes stay, and the six digests are unchanged.
- **The seal guard stays:** it now checks exactly the record the engine will read, so a poisoned or inconsistent stored record still fails the run (tested).

**Fixed:** commit `1200fec`, CI run [43198329615](https://github.com/rpahasara/cloud-autopsy/actions/runs/43198329615), both jobs pass.
- A run re-observing the same objects through an evolved registry seals and verifies, reading records bound to its own registry.
- Earlier runs still verify and read their own binding.
- `ca.evidence_version` still holds the first bytes.

**Other review items (not P0/P1):**
- **(P2) Secret names in Events.** An Event whose involved object is a Secret would store the Secret's *name* (never its content). The collector should withhold such events and count them (planned in 004e).
- **(P3) Plan-pin trigger strength.** The `0006` trigger accepts any combination of supported pins. Python refuses anything but the two whole profiles. Both profiles differ in one contract only, so no unsafe combination exists today.
- **(P3) Error type before migration.** `check_environment` against a database older than `0006` raises a database error ("relation does not exist") rather than `EnvironmentMismatch`. It is still a refusal.
- **(P3) Key names as data.** ConfigMap key names are kept unless they look credential-like, and a key name can itself be sensitive. Review the withholding rule before real data.

## <a id="limitations"></a>Limitations

- **Corroboration is not implemented:** Events cannot support a hypothesis yet. That needs a versioned rule change and new pins.
- **Times are limited:** `configmap_metadata` carries the creation time only. It cannot say *when* keys changed, and it is never a change.
- **Coverage stays narrow:** snapshot coverage is 1 ms per acquisition, so investigations from recordings will usually abstain, which is the honest result. Continuous coverage needs a watch-based collector.
- **Older packages:** a 0.1-only package cannot read 0.2 runs. Such runs appear unverifiable, not misread.
- **Reviews pending:** the vectors were computed independently by a second implementation, but no independent human contract review and no database or security review has been done.
