# CA-P2-004a — offline investigation creation from evidence bundles (implementation record)

**Scope:** the first slice of CA-P2-004 (see the [Phase 2 backlog](../../reviews/phase1d/phase2-backlog.md#status)). It adds a reusable way to create an investigation from a folder of evidence records, instead of from code-defined fixtures only. It is local and synthetic-only, under the product owner's [pre-gate development authorization](../ca-p2-003/ca-p2-003b-1.md).

**Not included:**
- collectors or any cluster, cloud or network access;
- an HTTP write endpoint (the API stays read-only);
- schema or contract changes;
- customer evidence or production credentials;
- UI changes.

This is not a gate approval, an evaluation result or a production-readiness claim.

## <a id="bundle"></a>Bundle format `ca-investigation-bundle/0.1-provisional`

A bundle is a directory holding exactly the records one investigation needs. It uses the existing contracts and adds no evidence schema:

| File | Contract |
|---|---|
| `bundle.json` | The manifest: `contract_version`, `bundle_id`, `data_classification` (must be `synthetic`), and for `registry`, `plan`, `clocks` and every batch a `{path, sha256}` entry |
| `registry.json` | `ca-source-registry/0.1-provisional` |
| `plan.json` | `ca-run-plan/0.2-provisional`, pinned to the registry digest |
| `clocks.json` | `{"clock_domains": [...]}`, declared clock-domain records |
| `batches/NNNN.json` | `ca-acquisition-batch/0.1-provisional`, in delivery order |

Every file is canonical JSON under the profile, so its SHA-256 in the manifest is stable.

**Examples:** the six synthetic variants are exported to `examples/bundles/<variant>/` by `tools/export_bundles.py`. They contain contract records only: no expected outcome, ground truth, secret or credential. A test requires them to equal a fresh export byte for byte, and `.gitattributes` keeps them byte-exact.

## <a id="validation"></a>Strict loading (`cloud_autopsy.app.bundle.load`)

Nothing is created until the whole bundle has passed every check below. Refusals carry a stable `code`, and messages never echo file contents.

| Check | Refusal code |
|---|---|
| Manifest shape, version and identifier; synthetic classification only | `bundle_manifest_invalid`, `bundle_version_unsupported`, `bundle_classification_refused` |
| Paths are lowercase relative names, at most one directory deep, `.json` only. No `..`, absolute, drive or backslash paths | `bundle_path_refused` |
| A file listed twice | `bundle_manifest_conflict` |
| Symlinks, Windows reparse points (junctions), hard links, special files, a junction as the bundle root | `bundle_link_refused`, `bundle_hard_link_refused`, `bundle_not_regular_file` |
| Any unlisted file or directory (so nothing else, such as ground truth, can travel inside a bundle) | `bundle_unexpected_entry` |
| Manifest at most 64 KiB; each record at most 1 MiB; at most 1,000 batch files; at most 32 MiB in total. These are checked from metadata before any record is read | `bundle_file_too_large`, `bundle_too_large`, `bundle_manifest_invalid` |
| The opened file is the checked file (no swap between check and read) | `bundle_file_changed` |
| SHA-256 matches the manifest; strict canonical JSON (no duplicate keys, BOM or floats) | `bundle_digest_mismatch`, `bundle_json_invalid`, `bundle_not_canonical` |
| Registry, plan (pinned to the registry), clock declaration and every batch (bound to the plan), validated by the same contract decoders as the database path. Unknown fields are refused | `bundle_record_invalid` (with the contract's code) |
| More batch files than the plan's `max_batch_deliveries` | `bundle_limit_exceeded` |

Two different batches delivered under one batch key are **evidence, not a structural error**. They are kept, and the engine reports the conflict, as in the `configmap-conflict` variant.

## <a id="creation"></a>Creating an investigation (`cloud_autopsy.app.create`)

**Offline mode** (`investigate_offline`):
- The engine runs on an in-memory seal of the bundle (`cloud_autopsy.app.offline`), with no database driver needed.
- The result is labelled **"offline: engine-checked, not database-verified"** and carries `verified = False`.

**Database mode** (`create_in_database`):
1. It runs the offline investigation first, so a bundle the engine cannot process never reaches the database.
2. As the least-privileged roles, through the existing pipeline (`pipeline.persist_records`, now shared with the fixture pipeline), it:
   - registers the registry and plan;
   - creates the run;
   - freezes the clock declaration;
   - ingests the batches in order;
   - seals the run.
3. It investigates the run as `ca_engine` and stores the result once as `ca_result_writer`.
4. It reads the result back through the verify-on-read loader the API uses, on a fresh `ca_engine` connection, and requires the bytes to equal the offline bytes.
5. Only then does it return a `DatabaseInvestigation`, labelled "database-verified".

**Failure handling:** any failure raises `CreationFailed` with the stage (`register`, `create_run`, `declare_clocks`, `ingest`, `seal`, `record_result`, `verify_on_read`, `compare_offline`), the run ID once it exists, and an error class name (never input content). A run that fails part-way is never presented as successful:
- before or at sealing it stays `collecting` (see R4 for a seal that fails after taking its lease);
- if it fails after sealing but before storing (`record_result`), it has no stored result, so the API answers `404 run_not_found`;
- if it fails after storing (`verify_on_read` or `compare_offline`), the stored result exists and is still checked on every read, but the creation is reported as failed;
- no grant is ever issued for it, in any of these cases.

## <a id="grants"></a>Private local grants and the dashboard

`issue_private_grant` accepts only `DatabaseInvestigation` objects, so a token is never created for an offline, failed or unverified run. It writes `grants.json` (the token's hash only) and `token` into a **new** private directory, and never reuses one:
- **Outside Git:** a directory inside any Git working tree is refused.
- **POSIX:** the directory is mode 0700 and the files are 0600.
- **Windows:** inherited permissions are removed, and the DACL is read back as SDDL by SID. It must be protected and allow only the current user, SYSTEM, Administrators and OWNER RIGHTS, the owner-only set Python 3.13 itself uses. `icacls.exe` is called from `System32`, never through `PATH`.

The API must accept the written grants file before the grant is used. The token is never printed, only its file path.

## <a id="cli"></a>Command line

```bash
python -I tools/create_investigation.py --offline examples/bundles/*
```

This is offline: no database, no Docker, and results are labelled "not database-verified".

```bash
.venv-db/bin/python -I tools/create_investigation.py examples/bundles/* --serve
```

This mode:
1. starts a disposable, loopback-only PostgreSQL (Docker; a free port is chosen);
2. creates and verifies each bundle;
3. issues a private token for exactly those runs;
4. serves the existing read-only API and dashboard on `127.0.0.1` until Ctrl+C;
5. then removes everything: the token directory as soon as the server stops (however it stops), then the database.

`--grant-dir DIR` chooses a new token directory, `--json` gives machine-readable rows, and `tools/export_bundles.py` re-exports the examples.

Exit status: 0 if every bundle succeeded; 1 if any bundle was refused or failed (nothing is served then); 2 for usage errors (for example `--serve` with `--offline`).

## <a id="tests"></a>Tests

- **`tests/app/test_bundles_offline.py`** (offline CI job):
  - **Examples:** they equal a fresh export and carry no outcome, truth or secret words. All six reproduce the existing result digests, with delivery order irrelevant, and the conflicting redelivery is kept as evidence.
  - **Refusals:** manifest shape, version and classification; unsafe paths; duplicate listing; unlisted files and directories; digest mismatch; non-canonical JSON and duplicate keys; size and count limits before reading; mismatched registry, plan and batch bindings, missing clocks and unknown fields; more batches than the plan allows; hard links, symlinks (Linux) and Windows junctions, including a junction as the root.
  - **CLI:** offline labelling and exit codes; `--serve` and `--grant-dir` refused with `--offline`; database failures reported with their stage; a missing database driver handled cleanly.
  - **Grants:** only for database-verified runs; written to a private directory outside Git (POSIX modes or the Windows DACL), never reused, accepted by the API loader, and removed when the server stops (Ctrl+C or an error).
- **`tests/integration/test_bundles.py`** (real-PostgreSQL CI job):
  - Every example is created and stored. Its stored bytes equal the offline result and the existing fixture pipeline's, and re-verify on read.
  - An injected failure at seal leaves the run `collecting`; one at storing the result leaves it `sealed` but unserved. In both cases nothing can be granted.
  - The CLI reports a refusal and a failure, and does not serve after a failure.
  - A created run opens in the existing Home (granted 1, resolved 1, "Verified on read") and in the Investigation workspace ("Byte-identical replay") in a real browser.
- **Example bundles in CI:** the offline CI job runs `tools/create_investigation.py --offline examples/bundles/*`.

## <a id="limitations"></a>Limitations and open items

- **Synthetic only.** Bundles must be classified `synthetic`. Real evidence needs the privacy and retention decision (CA-DEC-005) and a security review first.
- **No collector.** Bundles come from the exporter or are written by hand. A recorded-Kubernetes adapter (004c) and an isolated `kind` collector (004d, separate approval) come next.
- **Disposable database.** Database mode uses a disposable container, so the runs and the token disappear when the CLI exits. There is no persistent local store.
- **R4 was open in this slice:** a seal that fails after taking its lease left the run `sealing` until the lease expired. It is addressed in [004b](ca-p2-004b.md), together with run status in the API.
- **Windows ACL tolerance:** Administrators and OWNER RIGHTS are allowed on Windows token directories, matching Python's own private directories. Symlink refusal is exercised on Linux CI only, because Windows needs privileges to create symlinks; junctions are tested on Windows.
- **Not independent evaluation:** expected digests are the existing developer-authored regression values.
