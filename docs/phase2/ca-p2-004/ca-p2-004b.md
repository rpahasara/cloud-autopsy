# CA-P2-004b — run lifecycle, R4 recovery and run-scoped status (implementation record)

**Scope:** the second slice of CA-P2-004 (see the [Phase 2 backlog](../../reviews/phase1d/phase2-backlog.md#status)), stacked on [004a](ca-p2-004a.md). It resolves R4 from [003b-1](../ca-p2-003/ca-p2-003b-1.md), makes run lifecycle states reliable, and lets the read-only API and dashboard show the status of runs that have no verified result, under explicit run-scoped authorization. It is local and synthetic-only, under the product owner's [pre-gate development authorization](../ca-p2-003/ca-p2-003b-1.md). The product owner approved the additive migration `0005` for this slice.

**Not included:**
- collectors or any cluster, cloud or network access;
- an HTTP write endpoint (the new route is a read-only `GET`);
- changes to migrations `0001`–`0004`, tables, columns, triggers or earlier grants;
- a dashboard redesign;
- customer evidence or production credentials.

This is not a gate approval, a database or security reviewer approval, or a production-readiness claim.

## <a id="lifecycle"></a>Run lifecycle

The states and allowed transitions are unchanged from migration `0001`, which enforces them with `ca.check_run_transition` (every update increases `state_version` by exactly 1):

| From | To | Who and when |
|---|---|---|
| (new) | `collecting` | `ca_planner` creates the run |
| `collecting` | `sealing` | a sealer takes the lease (phase A) |
| `sealing` | `sealing` | a sealer takes over an expired lease, or re-acquires its own (counted as an attempt) |
| `sealing` | `sealed` | the lease holder publishes and verifies the frozen input (phase B) |
| `sealing` | `failed` | the lease holder hits a deterministic failure, or a sealer finds the attempts exhausted |
| `collecting` | `failed`, `cancelled` | allowed by the schema; not used by any code path yet |

`sealed`, `failed` and `cancelled` are terminal. A run is shown as **verified** only when it is `sealed`, its result is stored, and the result verifies on read; no other state is ever presented as verified.

## <a id="r4"></a>R4 fix and recovery semantics (`cloud_autopsy.db.seal`)

- **Deterministic failure → `failed`.** A contract error (`ContractError`, including `ManifestError`) from the pure seal, or from re-verifying what phase B wrote, gives the same result on every retry. The worker moves the run to `failed` with the fixed reason `seal:<contract code>` (for example `seal:limit_exceeded`) and raises `SealFailed`. The run no longer waits in `sealing` until its lease expires.
- **Transient failure → recoverable.** Any other error (a database or connection error, or a crashed process) leaves the run `sealing` under its lease. After the lease expires, any sealer may take it over (`seal_run` with a new worker). The seal is deterministic, so the recovered output is byte-identical (tested).
- **Bounded, durable retries.** While a run is `sealing`, its `state_version` is exactly the number of lease acquisitions so far:
  - every acquisition is a committed update;
  - the trigger forces `+1` per update;
  - nothing else updates a `sealing` run.

  The count therefore survives any process crash, with no new column. A worker that would make acquisition `MAX_SEAL_ATTEMPTS + 1` (provisionally 3 attempts) instead moves the run to `failed` with `seal:attempts_exhausted`.
- **Fencing stale workers.** Publication (phase B) and the move to `failed` both lock the run (`FOR UPDATE`) and require:
  - state `sealing`;
  - this worker's `state_version`;
  - this worker as the lease owner;
  - a lease that has not expired, compared with `clock_timestamp()` rather than the transaction start time.

  A worker whose lease expired, or was taken over, gets `SealConflict` and changes nothing.
- **A lease that expires during publication** (PR #29 review) is safe, and no code change was needed:
  - phase B checks the lease once, under a `FOR UPDATE` lock on the run row that it holds until commit or rollback;
  - every takeover or move to `failed` must take the same lock, so none can commit inside the publication transaction.

  Two real-PostgreSQL tests force the timing: the lease expires after the pages and rows are inserted and before the final `sealed` update, while a second worker, started only after expiry, is observed waiting on the lock.
  - **A commits:** the second worker then sees `sealed` and gets `SealConflict`; there is one byte-identical publication and no takeover (`state_version` 2).
  - **A fails before commit:** everything rolls back, and the second worker takes over the expired lease and seals byte-identically (`state_version` 3), with no rows left behind.

  A second check just before the final update would add nothing.
- **Atomic, idempotent publication** is unchanged: phase B publishes the root, pages and decoded rows in one transaction, verifies them before commit, and rolls back completely on any failure.

**Creation path:** `create_in_database` reports a deterministic seal failure as `CreationFailed(stage="seal", reason="seal:<code>")`, and the run is `failed`.

## <a id="migration"></a>Migration `0005_run_status_view.sql` and privileges

The migration is additive, forward-only and checksummed like the others. Migrations `0001`–`0004` are unchanged. It creates one view, `ca.run_status` (`security_barrier`, owned by `ca_owner`):

| Column | Content |
|---|---|
| `run_id` | the run |
| `state` | `collecting`, `sealing`, `sealed`, `failed` or `cancelled` |
| `failure_reason` | failed runs only: a `seal:<code>` value. Any other stored text, or none, becomes `unspecified`, so free text is never exposed |
| `lease_expired` | sealing runs only: whether the current lease has expired |

**What it never exposes:** evidence, plans, lease owners (worker identities), timestamps, state versions or exception messages.

**Privileges:**
- `SELECT` is granted to `ca_engine` only, the API's role, which has read-only transactions by default.
- `REVOKE ALL … FROM PUBLIC`.
- No write privilege anywhere.
- `ca_engine` still has no base-table access.

Tests check each of these.

## <a id="authorization"></a>Status authorization design

The problem: grants were issued only for verified runs, and the database role cannot tell callers apart. The design keeps both boundaries explicit:

1. **Run-scoped status grants.** Grants contract `ca-api-grants/0.2-provisional` adds `status_run_ids` to each grant:
   - it is disjoint from `run_ids`;
   - the two lists together name 1–1000 explicit UUIDs, with no wildcard;
   - version 0.1 files are accepted unchanged, and `issue` still writes 0.1 unless status runs are given.
2. **Status is not result access.** `Grant.authorizes(run)` (results, timeline, hypotheses, citations, evidence) still checks `run_ids` only, and those routes still serve only a result that verifies on read. A status-only run gets `403 run_not_authorized` on all of them, before the database is touched.
3. **New read-only route** `GET /v1/runs/{run_id}/status`:
   - it needs `may_view_status(run)`; an unlisted run is refused `403` before any lookup, so existence is not revealed;
   - it reads `ca.run_status` through the same verified-read gate;
   - it answers `{"verified": false, "access": "result"|"status", "lifecycle": {...}, "note": ...}`.
4. **Summaries** page through `run_ids ∪ status_run_ids`:
   - a status-only run is never passed to the result loader;
   - a result-granted run without a stored result is shown by its lifecycle state instead of `not_found`;
   - lifecycle items carry `state`, `verified: false`, `access` and `lifecycle` only, with no result fields:

     | Lifecycle | Summary item state |
     |---|---|
     | `collecting` | `collecting` |
     | `sealing` | `sealing` |
     | `sealed` with a result grant but no stored result | `awaiting_result` |
     | `sealed` with status-only access | `sealed` |
     | `failed` | `run_failed` |
     | `cancelled` | `cancelled` |
5. **Who gets status access.** `issue_private_grant(..., failed=[CreationFailed, ...])` grants failed creations whose run exists as status-only. A `CreationFailed` can never be granted results.

   In the CLI:
   - `--serve` alone still refuses to serve after any failure;
   - `--serve --status-for-failed` serves the verified runs with results and the failed runs as status only;
   - a refused bundle has no run, so nothing is served then;
   - the CLI also prints each failed run's lifecycle state (CLI status), for example `[run state: failed, seal:limit_exceeded; not verified]`.

The synthetic preview has no status loader, so its behaviour is unchanged.

## <a id="dashboard"></a>Dashboard

The design is unchanged:
- **Investigations table and Home:** lifecycle states appear in the existing Verification column and "Needs attention" counts, never as outcomes. The labels are "Collecting · not verified", "Sealing · not verified", "Sealed · no result yet", "Sealed · status only", "Run failed" (with its reason) and "Cancelled". In-progress states reuse the preview tone (amber) and failed states reuse the refusal tone (rose).
- **Run page:** opening such a run shows its status in the existing state panel ("Run failed", reason `seal:…`; "Sealing in progress", with a note when the lease has expired).
- **Mode chip:** it never says "Verified on read" for these runs.

## <a id="evidence"></a>Before and after

The failing regression tests were committed alone first (`410e18d`). CI run [43166329424](https://github.com/rpahasara/cloud-autopsy/actions/runs/43166329424) failed in the database job with:
- `test_a_deterministic_seal_failure_marks_the_run_failed`: `AssertionError: 'sealing' != 'failed'`. This is R4: the run stayed `sealing`.
- `test_a_worker_whose_lease_expired_cannot_publish`: `SealConflict not raised`. A worker with an expired lease could still publish.
- `test_recovery_is_bounded_and_counted_durably_across_crashes`: `Exception not raised`. Recovery was unbounded.
- `test_a_taken_over_worker_can_neither_publish_nor_fail_the_run`: `AttributeError … '_mark_failed'`. There was no fenced failure path.

The crash-recovery, live-lease and concurrent-recovery tests passed before and after, which shows that behaviour was preserved. After the fix (`8e98314` onward), every test passes; see the PR for the CI runs.

One existing test changed on purpose. `test_failed_publication_leaves_no_partial_manifest` used a lease that expired at once and still expected publication to be attempted. Publication now requires a live lease, so the test uses a 1-second lease and waits for it to expire before recovery.

## <a id="tests"></a>Tests

- **`tests/integration/test_lifecycle.py`** (real PostgreSQL):
  - a deterministic failure marks the run `failed`, and the run is terminal and unserved;
  - a worker with an expired lease cannot publish;
  - a taken-over worker can neither publish nor mark the run failed;
  - a live lease blocks other workers;
  - a crash between phases is recovered byte-identically;
  - four concurrent recoverers seal once;
  - attempts are bounded and counted durably across closed connections;
  - the `0005` view shows each state and only its four columns, never leaks the worker name or free-text reasons, and is readable only by `ca_engine` (not PUBLIC), with no write privilege.
- **`tests/integration/test_bundles.py`:**
  - a deterministic seal failure during creation is reported with `seal:limit_exceeded` and leaves the run `failed`, never verified or granted results;
  - in a real browser with a real database, a failed run served status-only shows "Run failed" with its reason, its result routes answer 403, and the verified run is still verified.
- **`tests/api/test_status_offline.py`:**
  - grants 0.2 rules (disjoint, bounded, explicit, with 0.1 unchanged);
  - status-route authorization ordering;
  - status access never opening result or evidence routes, and the result loader never called for status-only runs;
  - summary lifecycle items, including `awaiting_result`;
  - no change without a status loader.
- **`tests/browser/test_lifecycle_browser.py`:** lifecycle labels and tones in the existing table; the state panel for failed, sealing (expired lease) and status-only runs; no outcome counted; no console errors.
- The existing suites still pass, including all six synthetic scenario outcomes and their pinned result digests, the role and privilege tests (updated for the fifth migration), and the browser suites.

## <a id="limitations"></a>Limitations and open items

- **Provisional values:** `MAX_SEAL_ATTEMPTS = 3` and the 300-second default lease are unbenchmarked.
- **Derived attempt count:** the count comes from `state_version` and relies on the invariant that only lease acquisition updates a `sealing` run. If a future change adds another update to `sealing` runs, it must add an explicit counter instead.
- **No sweeper:** recovery happens when a sealer is invoked for the run (for example a retried creation). Nothing scans for runs whose lease expired.
- **Unused paths:** `collecting → failed` and `cancelled` exist in the schema, but no code path produces them yet. Ingest failures leave a run `collecting`.
- **Status scoping lives in the API:** `ca_engine` can read the status of every run through the view, and the API restricts lookups to the caller's grant. Row-level scoping in the database would need per-caller roles.
- **Disposable database only:** as in 004a, created runs and tokens disappear when the CLI exits.
- **No independent review:** these are AI-assisted changes. A database and security reviewer has not reviewed migration `0005`, the grant contract change or the fencing logic.
