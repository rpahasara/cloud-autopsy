# CA-P2-006b — local read-only investigation API (implementation record)

**Scope:** the second slice of CA-P2-006 (see the [Phase 2 backlog](../../reviews/phase1d/phase2-backlog.md)). It is a minimal, authenticated, read-only HTTP API over the verified results stored by [CA-P2-006a](ca-p2-006a.md). It is local, disposable and synthetic-only, under the product owner's [pre-gate development authorization](../ca-p2-003/ca-p2-003b-1.md).

**Not included:** write endpoints, a dashboard, collectors, AI providers, customer data and deployment. This is not a gate approval, an evaluation result or a production-readiness claim.

## <a id="routes"></a>Routes

All routes are `GET` only; any other method gets `405`.

| Route | Auth | Returns |
|---|---|---|
| `/healthz` | none | Liveness; no database access |
| `/readyz` | none | `200` only if the database answers as `ca_engine`, is classified synthetic, has this package's contract pins and runs read-only transactions by default; otherwise `503` |
| `/v1/runs/{run_id}/result` | token + run grant | The verified `ca-investigation-result/0.2-provisional` document |
| `/v1/runs/{run_id}/timeline` | token + run grant | Its deterministic timeline |
| `/v1/runs/{run_id}/hypotheses` | token + run grant | Hypotheses and outcome |
| `/v1/runs/{run_id}/citations` | token + run grant | Per hypothesis: cited evidence IDs, contradictions and limiting gaps; plus the manifest gaps and the outcome's citations |
| `/v1/runs/{run_id}/evidence/{evidence_hex}` | token + run grant | One sealed evidence record of that run. The path carries the 64-hex digest of `ca-evidence-id-sha256/0.1-provisional:<hex>` |

Every `/v1` response wraps its `data` in an envelope with `api_version`, `run_id`, `result_digest`, `verified: true` and the verification statement. Errors return only a stable code, plus a verification reason for `409`.

## <a id="security"></a>Security controls

- **Loopback only.** `LoopbackServer` binds `127.0.0.1` and refuses any other host. It uses the standard library only (`http.server`), with no new dependency and no other network service.
- **Authentication.** Bearer tokens are 32 random bytes, URL-safe encoded, and provisioned locally. The grants file (`ca-api-grants/0.1-provisional`) stores **only SHA-256 hashes**.
  - `grants.load` refuses a file inside any Git working tree, a file that group or others can access (POSIX), a file over 64 KiB, duplicate JSON keys, and any field outside the schema.
  - Token comparison uses `hmac.compare_digest` over every grant.
- **Run-level authorization.** Every grant lists its run IDs explicitly: 1–1000 canonical lowercase UUIDs, with no wildcard. A valid token for one run gets `403` on every other run.
  - A run outside the grant is refused **before the database is touched**, so the answer reveals nothing about whether the run exists.
  - A granted run that does not exist returns `404`.
- **Read-only database access.** Each request opens a new `ca_engine` connection and closes it afterwards. `ca_engine` is read-only by default and sees only the sealed views; the API holds no writer credentials.
- **Verify on read, no fallback.** A result, timeline, hypothesis, citation or evidence record is served only from what `results.load_verified_result` returns. That function re-checks the bytes, digest, columns and bindings, then re-runs the engine on the sealed evidence and requires byte-identical output.
  - Any verification failure returns `409 {"error": "result_unverifiable", "reason": <code>}` and never database rows.
  - Evidence is served only if it is one of that run's sealed members, re-derived during verification.
  - Results are not cached, so tampering is caught on the next request.
- **Strict input and size limits:**
  - path at most 256 characters (`414`), restricted to `[A-Za-z0-9/._:-]`, so there are no query strings, percent-encoding or spaces (`400`);
  - run IDs are canonical lowercase UUIDs and evidence digests are 64 lowercase hex characters (`400`);
  - any request body or `Transfer-Encoding` is refused (`413` or `400`);
  - headers are limited to 8 KiB (`431`);
  - responses are limited to 4 MiB (`500 response_too_large`);
  - socket timeout is 10 s; every response closes the connection.
- **Response headers:**
  - `Content-Type: application/json; charset=utf-8`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`;
  - `Content-Security-Policy: default-src 'none'`, `Referrer-Policy: no-referrer`;
  - a versionless `Server: ca-api`.
- **Logging.** The access log records method, path and status only, never headers, so it never contains tokens.

## <a id="result-write-boundary"></a>Result-write boundary (prerequisite, on PR #23)

Before this slice, PR #23 was corrected so that `store_result` re-verifies a submission against the sealed run, by exact replay, before the write-once insert. A forged first submission is rejected without being stored and cannot block the valid result. The remaining direct-SQL risk with compromised `ca_result_writer` credentials is recorded in [CA-P2-006a](ca-p2-006a.md#risks).

## <a id="run-it"></a>Run it

```bash
.venv-db/bin/python -I tools/api_demo.py
```

The demo:
- starts its own disposable, digest-pinned, loopback-only PostgreSQL;
- persists, seals and investigates the six synthetic variants and stores each result through the verifying write path;
- provisions two tokens into the private per-session secret directory: `reviewer` (all runs, plus one granted run ID that does not exist) and `single-run` (one run);
- serves the API on `127.0.0.1`;
- for every variant, retrieves the result, timeline, hypotheses, citations and every cited evidence record over HTTP, and checks that the served result bytes equal the stored bytes;
- checks refusals: no token, a wrong token, an ungranted run, a granted-but-unknown run, a write method, and a stored result tampered with during the demo (`409`, no data);
- writes `out/ca-p2-006b/summary.json`, then removes the container and secrets.

To run the server by itself against an existing disposable database:

```bash
python -m cloud_autopsy.api.server --grants /private/dir/api-grants.json --port 8765
```

It needs `CA_PG_SECRET_DIR`, which holds `ca_engine.password`, and `CA_API_DATABASE`.

## <a id="tests"></a>Tests

- **Offline** (`tests/api/test_api_offline.py`, CI offline job; no database, real HTTP on loopback):
  - token storage and strength, exact authentication, and no wildcard grants;
  - the grants file must be outside Git, private, and free of duplicates or unknown fields;
  - every route for all six variants;
  - run-level `403` without any backend call;
  - refusals: 401, 404, 409 (no data), 503, 400 for bad IDs, query strings and percent-encoding, 404 for traversal and unknown routes, 405, 413, 414 and 431;
  - the response-size cap, refusal of any non-loopback bind, and security headers.
- **Real PostgreSQL** (`tests/integration/test_api.py`, CI database job):
  - readiness;
  - all six stored results served verified, with **served bytes equal to the stored bytes** and every cited evidence record retrievable;
  - per-run authorization, 401, 404 for an unknown run, 405, and 404 for another run's evidence;
  - a stored result tampered with directly in the database gets `409` on every route, with no data.

## <a id="risks"></a>Unresolved risks and limitations

- **Bearer tokens over plain HTTP on loopback.** Any local process or user on the machine that obtains a token can use it. There is no TLS, token expiry, rotation or revocation list beyond editing the grants file and restarting.
- **No rate limiting or concurrency cap.** Each request re-runs the engine (CPU) and opens a database connection, so a local client can exhaust connections or CPU. Requests are bounded but not throttled.
- **Grant management is manual.** Grants are a hand-provisioned file and the server does not reload it. There is no audit log of access decisions beyond the access log.
- **Git-tree and permission checks are heuristics.** They look for a `.git` directory in parent directories and for POSIX mode bits. Windows ACLs are not checked.
- **Evidence content is untrusted text.** For example, a log `message` is served as JSON data; a future UI must treat it as untrusted.
- **Inherited from 006a:**
  - direct SQL with compromised `ca_result_writer` credentials can take a run's result slot (availability);
  - superuser or owner access can rewrite rows, but verify-on-read detects it;
  - results replay only under the engine versions their plan pins.
- **Real database only in CI.** PostgreSQL ran only in GitHub CI; Docker is unavailable on the development machine.
