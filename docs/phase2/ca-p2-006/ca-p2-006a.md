# CA-P2-006a — immutable investigation-result storage and replay (implementation record)

**Scope:** the first slice of CA-P2-006 (see the [Phase 2 backlog](../../reviews/phase1d/phase2-backlog.md)). It persists investigation results and replays them. It is local, disposable and synthetic-only, under the product owner's [pre-gate development authorization](../ca-p2-003/ca-p2-003b-1.md). It builds on [CA-P2-005a](../ca-p2-005/ca-p2-005a.md).

**Not included:** a public or local API, a dashboard, lifecycle purge, tombstones, exports, production data, live collectors and AI calls. This is not a gate approval, an evaluation result or a production-readiness claim. Gates D and I and the independent reviews remain open.

## What is stored

| Table (migration `0004`) | Content | Written by | When |
|---|---|---|---|
| `ca.run_clock_declaration` | One `ca-clock-declaration/0.1-provisional` document per run: the exact canonical bytes and their digest | `ca_planner` | Only while the run is `collecting`, so before sealing |
| `ca.investigation_result` | One `ca-investigation-result/0.2-provisional` document per run (columns listed below) | `ca_result_writer` (new role) | Only for a `sealed` run |

**`ca.investigation_result` columns:**
- the exact result bytes and their SHA-256;
- the result digest;
- the run ID and investigation ID;
- the plan digest and manifest digest;
- the clock-declaration digest;
- the result, engine, mechanism-catalog and timeline-rules versions;
- the outcome status.

Both tables are append-only: `UPDATE`, `DELETE` and `TRUNCATE` are refused by trigger, even for the schema owner.

## <a id="clock-declarations"></a>Clock declarations

A declaration is the canonical document below, where `clock_domains` is sorted by `clock_domain_id`:

```text
{"contract_version": "ca-clock-declaration/0.1-provisional",
 "registry_digest": <the run's registry digest>,
 "clock_domains": [<ca-time-interval clock-domain record>, ...]}
```

Its digest is `ca-clock-declaration-sha256/0.1-provisional:` followed by the SHA-256 of the exact bytes.

**Rules, enforced both in Python (`engine.clocks`) and in the database:**
- **Registry match.** It declares exactly the clock domains bound to the registry's sources, each once.
  - Python refuses a missing, extra or duplicated domain.
  - A database trigger compares the declared set with the registry snapshot.
- **Same run.** It belongs to its own run: a foreign key on `(run_id, plan_digest)` to `ca.run`, and on `(plan_digest, registry_digest)` to `ca.run_plan`.
- **Exact bytes.** The digest is the bytes' SHA-256, enforced by a `CHECK` that recomputes it. Its fields must equal its columns.
- **Fixed before sealing.** It can only be added while the run is collecting, and there is one per run.
  - A different second declaration is refused with `ClockDeclarationConflict`; an identical one is a no-op.
  - It can never be updated or deleted.
- **No caller-supplied clocks.** The engine reads clock assumptions only from the run's stored declaration (`db.results.investigate`), so a replay cannot use different ones. A sealed run without a declaration cannot be investigated (`clock_declaration_missing`).

## <a id="result-version"></a>Result contract `0.2-provisional`

The result now carries `inputs.clock_declaration_digest`. That changes the serialized contract, so the version moved explicitly:
- `ca-investigation-result/0.1-provisional` became `0.2-provisional`;
- its digest algorithm moved to `ca-investigation-result-sha256/0.2-provisional`;
- the plan pins `clock-declaration: ca-clock-declaration/0.1-provisional`.

A 0.1 result is neither produced nor accepted. The engine, catalog and timeline-rule versions are unchanged.

**Conclusions are unchanged.** `tests/engine/_semantic.py` defines a version-independent view of a result: the timeline, every hypothesis with its prerequisites, citations, orderings and contradictions, the gaps by kind, and the outcome. The view is pinned for all six variants to its value at `3cba5d3`, under 0.1 (`PreservationTests`), and the new 0.2 result digests are pinned too.

## <a id="write-once"></a>Write-once policy

| Submission | Result |
|---|---|
| First result for a sealed run | Stored |
| The same bytes again (a retry, or concurrent writers of the one deterministic result) | `IDENTICAL`; nothing is written |
| Different bytes for the same run | Refused (`ResultConflict`); the first result stays and nothing is overwritten |

**Nothing is quarantined.** The engine is deterministic, so two different results for one sealed input mean a defect or tampering. The refusal is the signal. Storing a second result for a run would also make it unclear which one is authoritative.

**One result per run.** A run's plan pins its rule versions, so a different engine version needs a new run with a new plan.

## <a id="fail-closed-writes"></a>Fail-closed writes (first-write poisoning fix)

**Problem** (PR #23 review): the first stored result for a run is permanent, and a different second one is refused. Up to `7c86a67`, `store_result` checked the submission's shape but not its reasoning. A self-consistent forgery submitted first through the application was therefore stored. Reads refused it (`replay_mismatch`), but the correct result could never be stored for that run: an availability loss, not a confidentiality or integrity loss.

**Fix:** `store_result(engine_db, writer_db, run_id, result_bytes)` is now the only supported write path, and it verifies before it writes.
1. It loads the sealed run and its clock declaration read-only, as `ca_engine`.
2. It requires canonical bytes, then runs `result.verify_result`: digest, citations, outcome consistency and **byte-identical replay** of the engine.
3. Only then does it insert, as `ca_result_writer`. The investigation ID comes from the sealed run, never from the caller.

A rejected submission writes nothing, so the correct result stays storable. `ca_result_writer` still cannot read evidence: verification uses the separate read-only `ca_engine` connection, and no database role trusts caller JSON. Append-only storage, idempotent retries and concurrent-writer behaviour are unchanged. The internal insert is now private (`_INSERT_RESULT`, `_result_row`).

**Tests** (real PostgreSQL):
- `test_forged_first_submission_is_rejected_and_does_not_block_the_valid_result` submits:
  - a replay mismatch, a substituted cause and non-canonical bytes; nothing is stored for any of them;
  - the forgery again; still refused;
  - the valid result; `STORED`, then `IDENTICAL` on retry;
  - a later forgery; still refused.
- `test_concurrent_forged_and_valid_writers_store_only_the_valid_result`: six concurrent writers, half submitting forgeries. Only the valid result is stored.
- `test_another_runs_valid_result_is_rejected_by_the_write_path` and `test_submission_for_an_unsealed_run_is_rejected`.
- `test_residual_risk_direct_sql_with_writer_credentials_can_still_poison_a_run` reproduces the remaining risk below.

## <a id="bindings"></a>Same-run integrity in the database

- **Composite foreign keys** from `ca.investigation_result` to:
  - `ca.run (run_id, investigation_id)` and `ca.run (run_id, plan_digest)`;
  - `ca.frozen_input (run_id, manifest_digest)`;
  - `ca.run_clock_declaration (run_id, declaration_digest)`.

  A result therefore cannot name another run's investigation, plan, manifest or clock declaration.
- **`ca.check_investigation_result`**, a `SECURITY DEFINER` function with a fixed `search_path`, checks that:
  - the run is `sealed`, which is a terminal state;
  - the plan pins exactly the stored result, engine, catalog and timeline versions;
  - the digest, versions, plan, manifest, clock-declaration digest and outcome columns equal the fields inside the stored bytes.

  It is `SECURITY DEFINER` because `ca_result_writer` has no grant on `ca.run` or `ca.run_plan`. EXECUTE is granted to no role, as for the existing definer functions.
- **`CHECK`** constraints recompute the SHA-256 of the result bytes and of the declaration bytes.

## <a id="verify-on-read"></a>Verify on read

`db.results.load_verified_result(engine_db, run_id)` returns a result only after checking all of the following. It runs as `ca_engine`, which is read-only and uses sealed-only views, in one `REPEATABLE READ READ ONLY` snapshot.

1. The stored bytes match their stored SHA-256 and are canonical JSON.
2. The contract version is `0.2-provisional`, and every stored column equals the field inside the bytes (`result_columns_mismatch`).
3. The result names this run's investigation, plan and sealed manifest (`result_binding_mismatch`), and this run's clock declaration (`clock_declaration_mismatch`).
4. The clock-declaration bytes match their digest and the run's registry.
5. The sealed evidence is reloaded and re-verified: `verify_full` on the manifest, and every evidence record is re-derived. The engine then runs again.
   - `result.verify_result` checks the digest, every citation and the outcome's consistency.
   - It also requires **byte-identical output**; otherwise the result is refused (`replay_mismatch`).

**A row's existence proves nothing.** A self-consistent forgery inserted with direct SQL is refused on every read, because re-execution cannot reproduce it. A test covers this.

**Defect found by the concurrency test.** The first CI run (`42825693276`) failed: concurrent writers got `23505` instead of `IDENTICAL`. `ON CONFLICT (run_id)` arbitrates only on the primary key, and a redundant `UNIQUE (run_id, result_digest)` was violated first.

**Fix:** the redundant constraint was dropped. Both inserts now use `ON CONFLICT DO NOTHING` without an arbiter column, so any unique constraint counts. Migration `0004` was edited before it had been applied to any persistent database; it exists only in this unmerged PR.

| Role | New privileges in `0004` |
|---|---|
| `ca_result_writer` (new; login) | `INSERT`, `SELECT` on `ca.investigation_result`; `SELECT` on the classification and contract pins. No other table, no `UPDATE` or `DELETE`. |

All SQL uses bound parameters.

**One-command demo.** `tools/investigation_demo.py` now does the following for every variant:
- stores result A once and retries the store, which must be a no-op;
- loads it back on a new `ca_engine` connection with full verification;
- requires stored = replayed = permuted = database-free bytes.

## <a id="risks"></a>Unresolved risks and limitations

- **Compromised `ca_result_writer` credentials (direct SQL).** Anyone holding the writer role's password can bypass `store_result` and `INSERT` a database-shape-valid forgery as the first result for a sealed run. The database checks bindings and bytes, not the reasoning.
  - **Reads stay safe:** verify-on-read refuses the forgery (`replay_mismatch`).
  - **Availability is lost:** the correct result can no longer be stored for that run (`ResultConflict`), and append-only storage means it is not repaired by deleting the row.
  - **Recovery:** a new run.
  - **Before production this needs stronger database-enforced attestation,** such as a signature from a separate verifier key checked by the database, or a verifier service as the only writer.
  - Reproduced by `test_residual_risk_direct_sql_with_writer_credentials_can_still_poison_a_run`.
- **Insider with database access.** Someone with superuser or `ca_owner` access, or `session_replication_role`, can rewrite rows. Verify-on-read detects every case tested, but it cannot recover the original. There is no off-database signature or transparency log yet.
- **Engine-version replay.** A stored result is replayable only by the same engine versions, which the run's plan pins. An engine upgrade makes older results unverifiable by the new code: they are refused as `result_version_unsupported` or `rule_versions_mismatch`, not reinterpreted. Re-verifying historical results needs the old engine kept alongside, or a new run.
- **Partial checks in the database.** The database checks bindings and bytes, not the reasoning. Only the engine replay validates the content, so a reader that skips `load_verified_result` and reads the view directly gets unverified bytes.
- **Clock-declaration timing.** A run sealed without a declaration can never be investigated. There is no repair path in this slice.
- **R4 (from #21) still open.** A failed seal leaves a run `sealing` until its lease expires.
- **Out of scope:** lifecycle purge, tombstones, deletion and replay races, export, and same-run API authorization (CA-P2-006b and later).
- **Real database only in CI.** PostgreSQL ran only in GitHub CI; Docker is unavailable on the development machine.
