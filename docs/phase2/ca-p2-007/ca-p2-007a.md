# CA-P2-007a: development-set evaluation of the incident milestone (protocol and record)

**Status:** the harness is implemented on a draft branch. The protocol below was fixed **before** any evaluation run. Results are added in [§Results](#results) as they come, and later fixes and reruns are reported separately from the first, untuned run.

**This is not independent accuracy certification.** It is a developer-authored synthetic development set ([milestone plan §12](../milestone-incident/plan.md#independent)).

## What is frozen before running

**Scenario definitions, truth and thresholds.** `tools/eval/scenarios.json` (`ca-eval-scenarios/0.1-provisional`) holds two positive and seven negative scenarios. For each scenario it gives:
- the initial workload settings;
- the injected action;
- the RBAC variant and any log bound;
- the **truth**: what was injected, never derived from a result;
- the expected outcome.

It also holds the approved thresholds. The evaluation records the file's SHA-256, and changing anything in it makes a new version.

**Baseline.** The evaluation runs from a branch `eval/ca-p2-007a-run-<n>` whose commit is the baseline. The job summary records:
- the commit SHA;
- the scenario digest;
- the kind and kubectl versions and the node image digest;
- the workload image digest (`python:3.13.9-slim-trixie@sha256:326df678…`);
- the engine, catalog and rule versions (rule profile 3).

**Collection, for every repetition:**
- recording 0.7, with Kubernetes Events not collected, declared before collection;
- pod logs, with the declared limit `checkout-api:DB_POOL_MAX`;
- a 150 s session with probes every 5 s;
- the incident window +20 s to +140 s, fixed;
- the scenario's action at +25 s;
- rule profile 3.

**Thresholds (approved):**
- P1 and P2: each at least **8 of 10** correct resolutions.
- Every negative repetition abstains.
- **0** false-cause selections.
- **100%** valid citations.
- **0** planted-data leaks.
- Byte-identical replay in every run.

## How runs are executed and scored

**Isolation and order.**
- Each repetition runs on its **own fresh kind cluster**, created and deleted around it (`tools/eval/run_rep.sh`).
- Repetitions run one at a time in a single job, interleaved round-robin across scenarios in a fixed order (`scenario.py order`). There are no parallel runs.

**Every attempt is recorded.** `tools/eval/evaluate_run.py` writes a record for each repetition. Nothing is retried or dropped, and a failed step still produces a record. A record contains:
- the status of every step;
- the offline outcome and its determinism;
- whether replay re-derives the bundle;
- the PostgreSQL verification;
- citation validity;
- a planted-data scan;
- coverage facts, including the window decision;
- timing facts, including how far after the window start the rollout bracket began.

**Truth is never shown to the product.** The collector, converter and engine never read the truth. A test (`tests/eval`) audits file opens during conversion, investigation and evaluation, and a static check confirms that no product module refers to the truth file.

**Scoring.** `tools/eval/score.py` is the only reader of the truth, and it runs after all repetitions. Each run is classified as one of:
- a correct resolution;
- a false cause;
- an unsupported resolution: a negative scenario whose cause exists but whose evidence was removed (N5, N6) resolved anyway;
- a necessary abstention;
- an unnecessary abstention;
- a harness failure.

Harness failures stay in the denominator: they never count as correct, and never as valid abstentions. The job fails when any criterion is not met.

**Harness smoke.** On pull requests, a smoke job (`incident-eval-smoke`) runs P1 repetition 0 to check the driver. Its record is never part of an evaluation.

## Timing sensitivity

In the first resolved run, the rollout's observed bracket began 28 ms after the incident window opened. The report lists this margin for every positive run, along with the positive runs whose window was not narrowed.

If the margin is found to be fragile, the window boundary will **not** be moved to improve scores. A separately versioned scenario correction would be proposed and evaluated as a new run.
