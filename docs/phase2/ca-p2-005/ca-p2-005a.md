# CA-P2-005a — first end-to-end deterministic investigation (implementation record)

**Scope:** the smallest runnable vertical slice of CA-P2-005 (see the [Phase 2 backlog](../../reviews/phase1d/phase2-backlog.md)). Local, disposable and synthetic-only, under the product owner's [pre-gate development authorization](../ca-p2-003/ca-p2-003b-1.md).

This is not a gate approval, an evaluation result or a production-readiness claim. Gates D and I, the CA-DEC decisions and independent reviews remain open. The scenario and every expected outcome in tests are developer-authored.

## Flow

1. **Input:** `cloud_autopsy.synthetic.scenario_001` supplies the predefined synthetic incident: a source registry, a plan, declared clock domains and collector batches for six variants. It contains no expected outcome.
2. **Persist:** `cloud_autopsy.app.pipeline.persist_and_seal` stores the run.
   - `ca_planner` registers the registry and plan and creates the run.
   - `ca_ingest` ingests each delivery idempotently, in any order, with duplicates and retries.
   - `ca_sealer` seals the run in two phases and checks the full manifest with `verify_full` before commit.
3. **Read:** `cloud_autopsy.db.read.load_sealed_run` reads as `ca_engine`, a new role with no base-table grants and read-only by default. It uses only migration `0003` views, which show sealed runs only.
4. **Verify input:** `cloud_autopsy.engine.inputs.build_input` refuses anything it can't verify:
   - it re-verifies the manifest against its recorded digest;
   - it requires the plan to pin exactly this engine's rule versions;
   - it re-derives every evidence record;
   - it requires the evidence set to equal the sealed membership exactly.
5. **Timeline:** `engine.timeline` keeps every source timestamp: raw text, clock domain, precision, local interval, and reference interval only when the clock is declared. Chronology is stated only by interval comparison. Overlaps, unknown continuity and unknown clocks stay `unordered`, with a basis.
6. **Mechanisms:** `engine.mechanisms` evaluates the explicit catalog `ca-mechanism-catalog/0.1-provisional`:
   - `config_limit_reduction` and `rollout_limit_reduction`, each once per observed change;
   - prerequisites with cited evidence and orderings, contradictions, and limiting gaps;
   - an `unobserved_change` placeholder when a gap may hide a change;
   - log message text is never read.
7. **Result:** `engine.result.build` produces `ca-investigation-result/0.1-provisional`, canonical JSON with a digest.
   - **Resolved:** only when exactly one hypothesis is supported and none is unresolved.
   - **Abstained:** otherwise, with machine-readable reasons and gap IDs, and no substitute cause.
   - **Synthesis:** reported unavailable.
8. **Verify result:** `engine.result.verify_result` re-checks the digest, every citation, outcome consistency and byte-identical replay.

## Variants and outcomes (current behaviour)

| Variant | Manifest | Outcome | Why |
|---|---|---|---|
| `config-cause` | complete | resolved: `config_limit_reduction` | change → load of the new value (same pod, ordered) → symptom (ordered); rollout contradicted (symptom precedes it) |
| `configmap-unavailable` | incomplete | abstained | failed mandatory ConfigMap acquisition: limiting gap, unobserved-change placeholders; rollout not confirmable |
| `configmap-conflict` | incomplete | abstained | two different batches under one key are retained and both excluded: batch-conflict gap |
| `clock-unknown` | complete | abstained | node clocks declare unknown continuity: load and symptom orderings unknown |
| `symptom-before-change` | complete | abstained | symptoms strictly precede the change: contradiction |
| `no-symptom` | complete | abstained | no symptom observed |

## Run it

With Docker and the hash-locked driver tree installed (see [db/README.md](../../../db/README.md)), run:

```bash
.venv-db/bin/python -I tools/investigation_demo.py
```

The command:
- creates a private secret directory and starts its own digest-pinned, loopback-only container under a unique Compose project;
- runs every variant twice, in canonical and in shuffled order with redeliveries;
- reads each run back as `ca_engine` and checks that canonical, permuted, replayed and database-free results are byte-identical;
- writes the results to `out/ca-p2-005a/`;
- always removes the container and the secrets.

## Tests

- **Offline:** `tests/engine/test_engine.py`, pure with no database. Runs in the offline CI job.
- **Real PostgreSQL:** `tests/integration/test_investigation_e2e.py`, plus the demo command, both in the `db-integration` CI job.

## Limitations

- **Scenario:** one synthetic scenario family with six variants. Two mechanisms and one mapped limit (`pool.maxConnections` to `POOL_EXHAUSTED`). Not a general investigation platform.
- **Clock domains:** declared by the scenario and passed to the engine. They are recorded in the result but not stored in the database.
- **Persistence:** results are files, not persisted; result storage, API and export belong to CA-P2-006.
- **Limiting gaps:** decided by source kind, so a gap on any Kubernetes query limits both mechanisms. This is conservative.
- **Timeline:** compares neighbouring entries only; the mechanisms compare the pairs they cite.
- **Evaluation:** no scorer, truth or independent evaluation (CA-P2-007).
