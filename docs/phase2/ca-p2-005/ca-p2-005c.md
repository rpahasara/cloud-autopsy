# CA-P2-005c: the engine on contract profile 4 (record)

**Status:** implemented on a draft branch for review. It is synthetic-only, provisional and unreviewed, and is not a gate disposition.

**Plan:** [milestone plan, revision 2](../milestone-incident/plan.md), decision M6 and [§5](../milestone-incident/plan.md#identity). **No mechanism, catalog or ordering-rule change.**

## What changed

1. **Rule profile 2 also accepts kinds 0.4.** Before this change it accepted contract profile 3 (kinds 0.3) only. It now accepts contract profile 4 (kinds 0.4) as well. The one-session-clock check (`observed_clock_domains_mixed`) applies unchanged.
2. **Kinds are mapped to source kinds through the pinned registry.** `limiting_gaps` decides which gaps limit a mechanism from the kinds a source kind produces. That mapping is now built from the kind registry the plan pins, instead of always from 0.1.
   - **Under 0.1–0.3** the result is the 0.1 mapping plus kinds that no mechanism needs, so every limiting-gap decision is unchanged.
   - **Under 0.4** a `kubernetes_api` source also produces `log_line`. A gap on it therefore limits every mechanism that needs logs. This is the fail-closed direction.
3. **Logs are bound to pod UIDs.** A log read through the Kubernetes API carries the sequence envelope and names the pod UID that the collector bound it to. If any such log under a pod name names a different UID from the single pod of that name, the name no longer identifies one pod, and the run abstains with `pod_identity_ambiguous`. Logs without the envelope (0.1–0.3) are bound by name only, exactly as before.

4. **Causal-scope guard: rule profile 3 (timeline rules 0.3; product-owner request, 2026-11-14).** Timeline rules 0.3 order exactly as 0.2, with one added rule. A change, or a symptom used as support, establishes a positive prerequisite only when its `observed` bracket lies entirely inside the plan window:
   - the rollout or ConfigMap change itself (`rollout_observed` or `change_observed` becomes `unsatisfied` / `outside_plan_window`);
   - the symptoms and configuration loads that support it.

   **What stays as before:**
   - Contradictions still use every observation, inside the window or not.
   - Identity evidence (pods, ReplicaSets) needs no bracket.
   - Profile 3, like profile 2, needs observed brackets (kinds 0.3 or 0.4) and a single session clock.
   - Profiles 1 and 2 are byte-for-byte unchanged. A new profile was needed because stored results are re-verified by exact replay, so the meaning of profile 2 cannot change.
