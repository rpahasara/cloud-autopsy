# CA-P2-002b — Timestamp provenance and clock-interval contracts (provisional)

Date: 2026-11-03. Backlog item: [CA-P2-002](../../reviews/phase1d/phase2-backlog.md), second slice after [CA-P2-002a](ca-p2-002a.md). Status: bounded preparatory development under product-owner direction. Gate D, Gate I, CA-DEC-003, the other CA-DEC decisions and contract approval remain open. Every rule and ceiling here is provisional until an independent architecture reviewer records a disposition.

## What the slice provides

`src/cloud_autopsy/contracts/timeinterval.py` implements contract `ca-time-interval/0.1-provisional`. It uses only the standard library, performs no I/O, and never imports the prototype.

| Element | Behavior |
|---|---|
| `parse_rfc3339` | Strict RFC 3339 parsing: ASCII digits, uppercase `T` and `Z`, an explicit offset (`Z`, `+HH:MM` or `-HH:MM`), 1–9 fraction digits, proleptic Gregorian years 0000–9999. Returns nanoseconds since the epoch, or raises a typed `TimeError` |
| `SourceTimestamp` | Keeps the raw text alongside the timestamp kind, clock-domain ID, parse status (`parsed`, `invalid`, `leap_second_unsupported`) with its reason code, epoch milliseconds, zone offset, an unknown-local-offset flag (`-00:00`), text, declared and effective precision, and an inclusive local interval in milliseconds |
| `ClockDomain` | `declared` or `unknown` status; offset (`source clock - reference clock`) with uncertainty, where null means unbounded; `fixture_declared` provenance only; continuity `declared_continuous`, `step_declared` or `unknown` |
| `reference_interval`, `compare`, `Ordering` | Interval correction and ordering with an explicit basis code |
| `from_record` | Strict decoding: the exact field set, the version checked, and every derived field recomputed from the raw text with types compared, so a forged interval is rejected |

Ten new time codes and five record codes were added to `errors.py`. The CA-P2-002a codes are unchanged; their pinned test now pins the 002a families separately.

## Provisional rules (product-owner direction)

1. **Milliseconds, widened outward.** Instants are stored as integer epoch milliseconds, with the raw text kept. The source is assumed to truncate, so the instant lies in `[t, t + precision)`. Bounds are widened outward to whole milliseconds and never rounded inward. Effective precision is the coarser of what the text shows and what the source declares, so a declaration can't narrow what the text implies.
2. **Strict parsing.** Invalid dates, times and offsets fail with stable codes.
3. **Leap seconds are not given an instant.** A leap-second timestamp is kept with status `leap_second_unsupported` and no parsed time. Any `:60` second is treated this way; there is no leap-second table.
4. **Offset correction.** A declared offset is subtracted and its uncertainty widens both bounds. The original timestamp is never changed.
5. **Declared offsets only.** Only fixture-declared synthetic offsets are accepted. Measured offsets are rejected, because measured-offset acquisition is out of scope.
6. **Doubtful clocks give no order.** A clock step, unknown continuity (which disables same-domain comparison), an unknown or missing clock, unbounded uncertainty, or an unparsed timestamp all yield `unordered` with a reason.
7. **Strict ordering.** A comes before B only when A's upper bound is strictly below B's lower bound. Touching or overlapping intervals are unordered.
8. **No tie-breaker.** Records have no ingestion-order, resourceVersion or evidence-ID field, and `compare` uses none. Identical intervals stay unordered whichever order they're passed in.
9. **Canonical values only.** Record values are integers, strings, booleans or null and are accepted by the canonical profile. Year 0000 to 9999 with the maximum offset and precision stays well within ±(2^53−1).
10. **Provisional ceilings:**
    - parsed text up to 64 characters;
    - raw text kept up to 256 characters;
    - precision up to 1 day;
    - offset and uncertainty each up to 366 days.

## Evidence

- **Vectors** (`vectors/ca-time-interval-0.1-provisional.json`):
  - 19 valid timestamps, 35 invalid timestamps and 17 comparisons over 6 declared clock domains.
  - Whole-second epoch values were computed with Python `calendar.timegm` and Node.js `Date.UTC`, which agreed. Fractions, offsets and interval bounds were derived by hand.
  - Every comparison is also checked in reverse.
- **Unit tests** (`test_time_contract.py`) cover:
  - every fraction length;
  - timezone equivalence and year rollover;
  - month lengths for 53 years from 0000 to 9999;
  - 500 random precision cases checking that the interval contains the instant and is never wider than needed;
  - clock-domain validation;
  - round trips through canonical bytes;
  - seven forged-record cases;
  - antisymmetry over 3,600 pairs and transitivity over 64,000 triples;
  - checks that no error message contains source text.
- **Prototype differential** (`test_time_prototype_differential.py`): loads the frozen prototype time model read-only, checks that both agree on epoch milliseconds for years 0001–9999 and on rejecting malformed input, and asserts each difference below exists.
- **Mutation probe:** 16 behavioral mutants were caught, among them a non-strict comparison, a flipped offset sign, no uncertainty widening, ignoring continuity, ignoring steps, treating unbounded as zero, rounding inward, accepting leap seconds, Unicode digits and skipping the forgery check. The one survivor removed a redundant `re.ASCII` flag, which changes nothing because the pattern already uses `[0-9]`.
- **CI:** the contract step was renamed "Contract tests (CA-P2-002a/b)"; its command is unchanged and now picks up the new test modules. All other steps are unchanged.

## Intentional differences from the frozen prototype (`ca-time/0.1-spike`)

| ID | Prototype | This contract |
|---|---|---|
| D1 | Rejects year 0000 (Python `datetime` minimum) | Accepts years 0000–9999 using integer calendar arithmetic |
| D2 | Accepts a trailing newline (`$` anchor) | Rejects it (full match) |
| D3 | Accepts non-ASCII digits (`\d`) | ASCII digits only |
| D4 | Leap second is a generic parse error | Raw text kept with status `leap_second_unsupported` |
| D5 | A declared 1 ms precision narrows a whole-second timestamp to one millisecond | The coarser of text and declared precision applies, giving a full second |
| D6 | Same-domain timestamps are always compared locally | Local comparison only with declared continuity; otherwise the reference interval is used |
| D7 | No clock-step concept | `step_declared` blocks all ordering involving that domain |

## Known limitations

- Truncation is assumed. A source that rounds would need a declared rounding mode, which this contract doesn't have.
- Continuity is declared per domain, not per window or step time. One declared step blocks ordering for the whole domain, even across unaffected periods.
- `-00:00` is recorded as a UTC instant with an unknown local offset, without further meaning.
- No IANA time-zone names, DST rules or leap-second table are used. Offsets come only from the text.
- Vectors were written by the implementer, and the arithmetic cross-check covers whole seconds only. A second reviewer should confirm the vectors before this contract leaves `-provisional`.

## Proposed next slice: CA-P2-002c — evidence records and identity

The slice would cover:
- observation and evidence records that embed `SourceTimestamp` and `ClockDomain` references;
- source-qualified identity with full SHA-256 evidence IDs;
- duplicate and conflict semantics, where an identical redelivery gives the same ID and the same identity with different content is a quarantined conflict;
- a versioned observation-kind registry in place of the prototype's fixed table;
- bounded attribute payloads.

**Decisions needed before it starts:**
1. Which fields make up an evidence identity (source identity, observation kind, source UID, source version), and whether a cluster or source alias is included.
2. The evidence-ID format: algorithm label plus 64 hex characters, as directed.
3. How conflicts are handled (quarantine record versus rejection) and what is retained.
4. The initial observation-kind registry and its versioning.
5. Payload size, depth and field ceilings, and which attribute fields are allowed.
6. Whether derived evidence and provenance edges are in 002c or deferred to 002d.

CA-P2-002c has not been started.
