# CA-P2-002c — Evidence identity and observation records (provisional)

Date: 2026-11-03. Backlog item: [CA-P2-002](../../reviews/phase1d/phase2-backlog.md), third slice after [CA-P2-002a](ca-p2-002a.md) and [CA-P2-002b](ca-p2-002b.md). Status: bounded preparatory development under product-owner direction. Gate D, Gate I, the CA-DEC decisions and contract approval remain open. Every contract, schema and limit here is provisional until independent architecture and security review.

## What the slice provides

Two modules, `src/cloud_autopsy/contracts/sources.py` and `src/cloud_autopsy/contracts/evidence.py`. Both use only the standard library, perform no I/O beyond their arguments, and contain ASCII-only source (now enforced by a test).

| Contract | Purpose |
|---|---|
| `ca-source-registry/0.1-provisional` | Reviewed configuration binding each `source_id` to a source kind, an opaque `cluster_id`, one namespace, its allowed clock domains and its query IDs |
| `ca-observation/0.1-provisional` | Untrusted observation input: `source_ref`, `observation_kind`, `source_uid`, `source_version`, `entity`, `times`, `attributes` |
| `ca-observation-kinds/0.1-provisional` | The seven synthetic kinds, with an evidence class, the producing source kind, the entity kind, allowed timestamp kinds and a closed attribute schema |
| `ca-evidence/0.1-provisional` | `ObservedEvidence` records and the in-memory ledger snapshot |
| `ca-evidence-id-sha256/0.1-provisional` | Evidence identity algorithm |
| `ca-evidence-content-sha256/0.1-provisional` | Content digest algorithm |

## Identity and content-digest semantics

| | Evidence ID | Content digest |
|---|---|---|
| Format | `ca-evidence-id-sha256/0.1-provisional:<64 hex>` | `ca-evidence-content-sha256/0.1-provisional:<64 hex>` |
| Input | Canonical bytes of `{algorithm, source_id, cluster_id, namespace, observation_kind, source_uid, source_version}` | Canonical bytes of `{algorithm, observation_kind, source_ref, source_uid, source_version, entity, times, attributes}` |
| Where `cluster_id` and `namespace` come from | The registry binding only. An observation that carries `cluster_id` is rejected as an unknown field, and `entity.namespace` must equal the bound namespace | Not included; the binding is not content |
| Times | Not included | Source inputs only (`timestamp_kind`, `raw`, `clock_domain_id`, `declared_precision_ns`), sorted by timestamp kind. Parsed intervals are derived and excluded, so a later time-contract revision does not change content |
| Set-valued attributes | — | `changed_fields` and `config_refs_*` are sorted and must be unique. Other lists keep their order |
| Excluded | Delivery metadata, registry ID, registry version | Delivery metadata (`query_id`, `batch_id`, `attempt`), which is validated against the binding and then discarded; the binding digest; derived time fields |

Consequences:
- **Identical redelivery** in any order, with any delivery metadata, gives the same ID and digest. The `deploy`/`deploy-reordered` vectors cover this.
- **Same identity, different content** gives the same ID and a different digest.
- **Same object through a source bound to another cluster** gives a different ID with the same content digest.
- **Rebinding a source** to a new cluster or namespace changes every identity from that source.
- **Prototype IDs** (`ev:<class>:<24 hex>`) and any other algorithm label are rejected by `parse_evidence_id`.

`ObservedEvidence.from_record` re-derives everything from a stored record using the registry:
- an evidence ID that doesn't match the identity fields gives `evidence_id_mismatch`;
- a content digest that doesn't match the content gives `content_digest_mismatch`;
- any other altered binding, class or derived time field gives `record_inconsistent`.

## Conflict handling

`EvidenceLedger` is an order-independent, in-memory classifier:
- One identity with one digest is `authoritative`.
- An identical redelivery is a `duplicate`.
- A second digest for the same identity is `conflict_quarantined`, and the identity becomes `conflicted`. Every variant is retained, sorted by digest, and `authoritative()` returns `None`. The conflict is sticky: redelivering the original afterwards is also quarantined.
- No record is overwritten or deleted.
- Each `admit` re-verifies the record through `from_record`, so a record with a forged digest is rejected before it can affect the ledger.

The final ledger state doesn't depend on delivery order. A test checks 302 delivery orders for identical snapshot bytes, and 200 random delivery sequences confirm that no identity is ever authoritative under two digests. Per-delivery outcomes such as `accepted_new` do depend on order and aren't part of the snapshot.

**This isn't concurrency protection.** The classifier is a pure in-memory function with no atomicity, persistence or isolation. Enforcing the same rule atomically in storage (unique identity, compare-and-quarantine in one transaction) belongs to CA-P2-003.

This is close to the prototype's behavior, which drops a conflicted identity from the sealed set. The difference is that the contract keeps every conflicting variant for inspection rather than discarding it.

## Bounded kind schemas (provisional limits)

**General limits:**
- Each observation is at most 65,536 canonical bytes, with 1–4 timestamps and at most 32 items per list.
- Log `fields` hold at most 16 entries, each a name matching `[a-z][a-z0-9_]{0,63}` with a value of at most 256 characters.
- Free-text values are at most 256 characters; a log `message` is at most 1,024.
- `restart_count` is between 0 and 1,000,000. Delivery attempts are between 1 and 100.

**Text rules:**
- Text never contains C0 or C1 controls, DEL, U+2028/U+2029, bidirectional overrides, a BOM or lone surrogates.
- Structured fields such as names, images, paths, metric names, decimal strings and durations each have a fixed ASCII character set.
- Numbers that need decimals (metric values and thresholds) are decimal strings, never floats.

**Kinds:**

| Kind | Source kind | Entity | Timestamps | Notes |
|---|---|---|---|---|
| `configmap_change` | kubernetes_api | ConfigMap | event | Before and after values must match their SHA-256 fields; `actor` is an unauthenticated label |
| `deployment_rollout` | kubernetes_api | Deployment | event, optional completed | `field_changes` values are hash-checked; three set-valued lists |
| `replicaset` | kubernetes_api | ReplicaSet | event | |
| `pod` | kubernetes_api | Pod | event, optional terminated | `configmap_volumes` with absolute mount paths |
| `log_line` | loki | Pod | event | `pod` must equal `entity.name`. `template: null` means the line matched no template, and then `fields` must be empty. `message` is kept as inert, untrusted text |
| `metric_sample` | prometheus | Service | event | Decimal-string value |
| `alert_firing` | prometheus | Service | event, optional active_since | |

**What can't get in:**
- There are no open-ended objects. Unknown attributes are rejected (`attribute_unknown`), and log field names that look like credentials (`password`, `secret`, `token`, `api_key`, `authorization`, `session`, `cookie` and similar) are refused with `attribute_forbidden`.
- No field is executable or interpreted. A hostile instruction in a log message, such as variant C's "approve and run kubectl delete", stays data.

**Timestamps** use the CA-P2-002b contract. An invalid or leap-second timestamp is kept with its parse status and no instant, and comparisons involving it are `unordered`/`unparsed_timestamp`. Clock domains must be bound to the source.

**Observed versus derived:** only `origin: observed` records exist. A record with any other origin is rejected. Derived evidence, provenance edges, causal relations and storage constraints are deferred.

## Evidence

- **Vectors** (`vectors/ca-evidence-0.1-provisional.json`):
  - a four-source registry, 11 observations covering all seven kinds, 4 relations, 21 invalid cases and 2 ledger scenarios;
  - the expected IDs and digests were computed by a separate JavaScript implementation of the rules above on Node.js v22.17.0, and the Python implementation matches all 11.
- **Unit tests** (`test_evidence_contract.py`) cover:
  - registry validation and digest stability;
  - delivery metadata being neither identity nor content;
  - delivery scope checks;
  - rebinding;
  - prototype and foreign ID rejection;
  - round trips for every vector;
  - ten tamper cases;
  - size and count ceilings;
  - credential-like keys;
  - inert hostile text;
  - pinned kind and code registries;
  - order-independent ledger snapshots;
  - no identity being authoritative under two digests;
  - sticky conflicts;
  - forged-digest rejection with an unchanged ledger;
  - error messages never echoing observed values or keys.
- **Prototype differential** (`test_evidence_prototype_differential.py`): all 74 development-fixture observations, base and variant additions, are accepted, and identity equivalence classes match the prototype's. The differences below are each asserted.
- **Mutation probe:** 16 mutants were run on `evidence.py`, and 15 are caught. Two of those (the source-kind check and fields on an unmatched log line) survived the first run and are now covered by added tests. The remaining survivor drops a redundant sort of timestamps that `observe` has already sorted.

## Intentional differences from the frozen prototype (`ca-evidence/0.1-spike`)

| ID | Prototype | This contract |
|---|---|---|
| E1 | `ev:<class>:<24 hex>` IDs | Full SHA-256 under a versioned algorithm label; prototype IDs are rejected |
| E2 | `sha256:` content digests | Versioned content algorithm label |
| E3 | Identity has no cluster or namespace binding | Identity includes the registry-bound `cluster_id` and `namespace` |
| E4 | List order is part of content | Set-valued lists are sorted |
| E5 | Open attribute objects | Closed, bounded per-kind schemas |
| E6 | Any namespace accepted | `entity.namespace` must equal the source binding |
| E7 | Conflicted identities are dropped | Every conflicting variant is quarantined and retained (documented, not asserted against prototype internals) |

## Changes to earlier slices made here

- `canonical._string` gains a fast path that skips `str.translate` when a string has nothing to escape. Output is byte-for-byte identical: every 002a vector, the property tests and the stdlib differential still pass. It encodes typical strings about 3.3 times faster, which keeps evidence re-verification affordable.
- The CI contract step was renamed "Contract tests (CA-P2-002a/b/c)"; its command is unchanged.
- `errors.py` gains the `EVIDENCE_CODES` family and `EvidenceError`. Earlier families are unchanged and pinned.

## Observations and risks

- **Wall-clock unit test (CA-P2-002a):** `test_large_inputs_finish_quickly` asserts each large input finishes in under 5 seconds. It took 8.2 seconds once during PR #17, and here 5.2 and 5.6 seconds while this machine was heavily loaded; the whole suite swung between 3 and 116 seconds. That's a CI flakiness risk.
  - **Recommendation:** keep a deterministic correctness test that asserts only the error codes for those inputs, and move timing into a separate, non-gating performance benchmark that records its environment.
  - The threshold has not been changed here.
- **Escaped characters turned literal:** my file-writing tool turned `\uXXXX` escapes into literal characters. In earlier slices that left literal non-ASCII characters, including U+2028, in some test files and vector data. Behavior is unaffected, but invisible characters in source make review harder. Product source under `src/cloud_autopsy` is now required to be ASCII by `test_product_source_is_ascii_only`. Test files and vectors aren't covered yet.

## Known limitations and unresolved decisions

1. **Registry trust:** the registry is trusted configuration passed in by the caller. Pinning its digest into a reviewed run plan, and authenticating the collector that supplies `source_id`, are later work (CA-CON-001/002, CA-P2-004).
2. **Credential detection is limited:** the key denylist is a heuristic, and values aren't scanned for secrets. Redaction and canary checks remain CA-SEC-005 work.
3. **ConfigMap values are retained:** the before and after values are kept in the content. Whether to store only digests for sensitive keys is a privacy decision (CA-DEC-005).
4. **The kind schemas are shaped by the development fixtures.** Real Kubernetes, Prometheus and Loki shapes need review before collectors exist.
5. **Conflict policy:** a conflict leaves no authoritative record. Should a conflicted identity become a gap (`unverifiable`) in the manifest, and should conflicts expire? This is for CA-P2-002d and CA-P2-005.
6. **Re-verification cost:** each admission re-verifies the record, so it costs one full validation. That's acceptable at fixture scale and unmeasured at larger scale.
7. **Not yet reviewed:** the vectors were written by the implementer and cross-checked by a second implementation by the same author. They need independent review.

## Proposed next slice: CA-P2-002d — acquisition batch, run plan and frozen-input manifest

The slice would cover:
- `RunPlan` (CA-CON-001), pinning the source-registry digest, expected sources and queries, a window and finite limits;
- `AcquisitionBatch` (CA-CON-002), with typed outcomes (complete, partial, empty, failed, denied, truncated), coverage windows, an opaque cursor and per-batch idempotency;
- `FrozenInput` manifest (CA-CON-003), listing sorted evidence IDs with content digests, the exclusion list of volatile fields and versions, and explicit gap records for missing sources, truncation and conflicted identities.

**Decisions needed before it starts:**
1. The outcome taxonomy, and what a clean empty result proves.
2. How conflicted identities appear in a manifest (as a gap type, or a separate list).
3. Finite per-plan limits for records, bytes and windows.
4. Whether a manifest may include `partial` acquisitions.
5. Where the registry digest is pinned.

CA-P2-002d has not been started.
